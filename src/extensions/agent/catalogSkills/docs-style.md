# Documentation in a house style

Edit the style rules to your own; the steps stay the same.

## Steps

1. **Know the reader** and what they want to do when they open the page. Write for that task.
2. **Check the facts:** every command, setting and path you mention exists as written (run or
   search for it). Examples must work when pasted.
3. **Draft** in the style below; then cut: every sentence should help the reader do the task.
4. **Match the neighbors:** in an existing docs folder, follow its structure, front matter and
   link style.

## Style

- Sentence case for headings and buttons ("Add a server", not "Add A Server").
- The reader is "you"; the software is named, not "we".
- Short sentences, one idea each. Lists for steps, tables for comparisons.
- Lead with what to do, then why. Put warnings before the step they're about.
- Code, commands, settings and file names in `code`. UI labels in **bold**, as shown on screen.
- No "simply", "just", "easy": what's easy for one reader isn't for another.
